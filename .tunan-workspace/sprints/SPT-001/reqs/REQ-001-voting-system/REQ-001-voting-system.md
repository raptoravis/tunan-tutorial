# REQ-001 — 轻量群体投票系统

## 用户原话

> 我想做一个投票系统：可以投票去哪里旅游 / 中饭吃什么。

来源：`.tunan-workspace/raw-reqs/SPT-001/2026-05-12-voting-system.md`

## 意图（一句话）

提供一个轻量的、可被任意小组使用的群体投票工具：发起人创建话题与若干选项，参与者通过分享链接进入投票，投完即可看到聚合结果。

## Goals

- **G-001 创建投票话题**：发起人能输入一个标题、2..N 个选项，选择单选或多选模式，可选地设置截止时间，提交后获得一个可分享链接。
  - [ ] AC-001-a：标题非空、选项 ≥2 才能提交，否则前后端均返回明确错误
  - [ ] AC-001-b：成功创建后页面展示分享链接（短路径，如 `/p/<id>`），点击复制可用
  - [ ] AC-001-c：截止时间为可选；不填则永不截止

- **G-002 参与投票**：任意持有分享链接的人可进入投票页，提交后立即看到聚合结果。
  - [ ] AC-002-a：单选模式下选中即可提交；多选模式下至少选 1 项才能提交
  - [ ] AC-002-b：提交成功后页面切换为结果视图（含每项票数与百分比），无需刷新
  - [ ] AC-002-c：已截止的投票仅展示结果，禁用提交按钮并提示"已截止"

- **G-003 防重复投票（基础）**：同一浏览器对同一话题默认仅可投票一次。
  - [ ] AC-003-a：服务端写一条 cookie（HttpOnly + SameSite=Lax）记录该浏览器已投过的话题 id 集合
  - [ ] AC-003-b：携带该 cookie 再次提交同一话题，服务端返回 409 并提示"你已投过此话题"
  - [ ] AC-003-c：在显著位置提示"匿名 cookie 去重，并非强身份认证"，避免误导

- **G-004 查看结果**：任何人通过链接均可查看当前结果（已投者直接看，未投者投完即看）。
  - [ ] AC-004-a：结果区按票数倒序展示，含票数、百分比、总票数
  - [ ] AC-004-b：结果区设置 `aria-live="polite"`，方便辅助技术读出更新

- **G-005 内置示例话题模板**：首页提供"去哪旅游"/"中饭吃什么"两个一键填充模板，降低首屏门槛。
  - [ ] AC-005-a：首页两个按钮，点击后跳转到创建页且选项已预填
  - [ ] AC-005-b：预填内容可被发起人编辑后再提交

## Constraints

- Web 平台，PC + 移动响应式
- 持久化：SQLite（单文件，便于教学/演示）
- 不引入登录/账户系统
- a11y：键盘可达 + 适当 aria 属性
- 性能：单实例 SQLite 在 100 票/话题 / 1000 话题量级内 p95 响应 < 300ms

## Non-Goals

- 实时滚动结果（websocket 推送）
- 多用户登录 / 个人投票历史
- 评论 / 讨论
- 私密投票（基于密码或邀请码）
- 截止后自动发邮件 / 通知
- 反爬虫 / 严格防刷（cookie 去重就够，承认 known limitation）

## Scope Boundary

**In**
- 创建话题、投票、看结果三件套
- 单选 / 多选切换
- 可选截止时间
- cookie 级去重
- 两个示例模板

**Out**
- 用户系统、社交分享卡片渲染、二维码生成、CSV 导出、管理后台、投票编辑/删除（首版不支持发起人修改自己已创建的话题）

## Research Findings

基于通用 polling app（Doodle / StrawPoll / Rallly 等）的常见模式总结：

- **匿名 + cookie 去重** 是同类工具的主流做法，既保证低门槛分享，又给出"基础不刷票"承诺。完全无防刷会被几秒钟攻破；强登录又劝退一次性场景。
- **投完即看** 避免羊群效应的最常见折中：发起人不必等截止，参与者也不会在投票前被多数意见带跑。
- **截止时间可选** 比强制截止更友好——"今晚吃啥"这种话题往往无固定截止。
- **a11y**：选项使用 `<label>` 关联 `<input>`；结果区 `aria-live="polite"`，键盘 tab 顺序与视觉顺序一致。
- **常见坑**：选项重复（trim 后比对）、选项过长造成 layout 破坏、URL id 可被穷举 → 用足够长的随机短码（≥8 字符 base62）。
