# tunan-align — top 3 + 默认推荐 对齐器

> **设计原则**：sponsor 不擅长开放回答（见 USER.md），只擅长选择。所有 tunan-* skill 在面对决策点时**必须**走这个统一壳，不要各自发明问法。

## 何时被调用

- 直接：sponsor 说 `/tunan-align <主题>`
- **间接（主要）**：其他 tunan-* skill 内部遇到决策点时，按本 skill 协议生成问题块；sponsor 选完后回到原 skill

## 协议（其他 skill 调用时的格式合同）

每个对齐点必须呈现为下面这种**统一格式**：

```
**对齐 Q<n>**: <一句话问题>

| #  | 选项                  | 说明（≤1 行：优势 / 风险 / 适用场景） |
|----|-----------------------|----------------------------------------|
| A  | ★ <推荐项>            | <为何推荐：默认/最常见/最低风险/最契合>  |
| B  | <次选项>              | <差异点>                              |
| C  | <第三项>              | <差异点>                              |
| 其它 | 自由文本              | sponsor 直接写                        |
```

**硬性约束**：
- 候选 ≤ 3，**必须**有且只有 1 个标 ★ 默认
- ★ 必须可独立成立（即"全部默认"=只采 A，不需追问）
- 每选项一句话说明，禁止长论证（USER.md：用摘要替代原始输出）
- 同时呈现多个 Q 时，编号 Q1/Q2/...，**单批最多 4 题**；超出必须分批，按"对下游决策影响度"排序，先问影响大的，等本批回答后再出下一批
- 优先使用 `AskUserQuestion` 工具（原生支持 1–4 题、每题 2–4 选项、★ 默认在 label 末尾加 `(Recommended)`），仅在工具不可用 / 选项含长说明 / 需对照大表时才退回 markdown 表
- **所有选项必须用单字符编号**：`1/2/3/4` 或 `A/B/C/D`，让 sponsor **单键可回**。禁止"accept all"、"全部默认"、"选写"、"调整"等需要拼写的词当选项标识 — 它们可以作为**选项的内容**但前面必须挂一个单字符编号
- **组合选项必须预先单独编号**：不要让 sponsor 自己拼"A+B" / "1+3"；如果有意义的组合就直接列成新选项（e.g. `4. A+B 一起做 — 两条不冲突`）
- "是 / 否"型确认也必须编号：`1. 是 / 2. 否`

## sponsor 的回应方式（必须支持的所有形式）

| 输入 | 解析 |
|---|---|
| `Q1=B Q3=C` | 仅这两条改非默认，其余默认 |
| `B、A、C` 或 `BAC` | 按顺序对应 Q1 Q2 Q3 |
| `全部默认` / `accept all` / `默认` / `用 A` | 全数采 ★ |
| `Q2 自定义：xxx` | 自由文本 |
| 直接长文本 | 视为对当前最近一条 Q 的自由回答 |
| 沉默 / 跳过 | **不**自动默认（要求明确意图）|

`accept all` 是一种**会话级状态**：sponsor 一旦说出，**后续所有未决策点直到流程结束或 sponsor 显式撤销**都自动取默认。skill 必须在状态生效与失效时各播报一次。

## 决策记录

每次对齐结果落到对应 artifact 的 **Open Questions** / **Decisions** 表：

```
| Q  | 问题       | 决议 | 来源       |
| Q1 | 优先级？  | P2   | accept all |
| Q2 | 是否纳入X | 是   | 显式 A     |
```

`来源` 字段必填：`accept all` / `显式 <字母>` / `自由文本`，便于 retro 复盘。

## 何时**不**走 align

- 纯展示信息（不需 sponsor 决定）
- 候选超过 3 个：**先收敛到 3**，不要给 5 个候选稀释默认
- 完全开放问题（无可枚举候选）：先用 `tunan-grill` 转成可枚举，再回到 align

## 反模式（自检）

- ❌ 强行凑 3 个候选（B/C 是注水的"好像也行"）
- ❌ ★ 默认其实风险最大但写法显得最稳妥
- ❌ "你看着办" / "都可以" — 永远不要把决策推回 sponsor
- ❌ 重复问已决策点 — 必须读上游 artifact 的 Decisions 表
- ❌ 一次性堆 ≥5 个 Q 让 sponsor 一起选 — 要分批 ≤4，先问影响最大的
- ❌ 在终端能用 AskUserQuestion 时仍硬上 markdown 大表
- ❌ 选项用单词或词组当标识（"accept all / 调整 / 否"），让 sponsor 拼写回答 — 必须挂单字符编号（来源 RETRO-007）
- ❌ 把"A+B"留给 sponsor 自己拼 — 有意义的组合应预先列为独立编号选项

## 示例（真实形态）

> **对齐 Q1**: 投票截止后再投，前端怎么处理？
>
> | # | 选项 | 说明 |
> |---|------|------|
> | A | ★ 提交按钮置灰 + tooltip "已截止" | 最低误操作；与多数投票工具一致 |
> | B | 仍允许提交但服务端 409 | 客户端简单，但用户挫败 |
> | C | 截止前 N 分钟黄条提示，截止后整页 readonly | 体验最好，工作量最大 |
>
> **对齐 Q2**: 截止时间精度？
>
> | # | 选项 | 说明 |
> |---|------|------|
> | A | ★ 分钟级 | 与日历约会习惯一致 |
> | B | 秒级 | 适合抢购场景，不适合投票 |
> | C | 仅日期 | 太粗 |

## 接下来做什么

被其他 skill 内调时，把决议回写到 artifact 后**返回原 skill 继续推进**，不要在这里产出"接下来做什么"——那是上层 skill 的事。

直接调用时：
```
✅ 对齐已记录到 <artifact>。
推荐下一步：
  1. ★ 回到原 skill 继续 (/tunan-<x>)
  2. /tunan-prime 看看现状
```
