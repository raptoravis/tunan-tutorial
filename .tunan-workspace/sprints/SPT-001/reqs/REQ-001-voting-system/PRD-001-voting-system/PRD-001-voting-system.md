# PRD-001 — 轻量投票系统

## Background

源自 [REQ-001](../REQ-001-voting-system.md)。sponsor 希望有一个**轻量级 Web 投票工具**，朋友 / 同事 / 小团队可以围绕开放议题（出游目的地、午餐选项等）发起投票、匿名参与、实时看到票数。本期定位为**单机可部署的最小可用版本**，不做账号体系、不做强反作弊。

## Personas

- **P-1 发起人 Aria**：群里的"组织者"。希望 30 秒内把候选项列出来发链接到群里，最好能看到谁还没投。需要发起、追加候选项开关、关闭投票的能力。
- **P-2 参与者 Bo**：被拉进群投票的同事。希望点链接就能投、不要注册，看到当前实时票数即可决定要不要补投。

非本期 personas（写明）：旁观者、跨团队管理员、机器人发起者 — 全部 Non-Goals。

## Functional Requirements

> 编号与 REQ Goals 对齐，便于追溯。

### FR-1 创建投票（源 G-001）
- FR-1.1 创建表单包含：标题（≥1 字符，≤120 字符）、候选项列表（≥2 项，每项 ≤80 字符）、「允许参与者追加候选项」开关（默认关）
- FR-1.2 提交后服务端生成 **房间 id**（短链友好，如 8 位 base62）与 **管理 token**（发起人本地保留，用于关闭投票/删除候选项）
- FR-1.3 创建成功页展示房间链接（可一键复制）与管理 token；提示发起人保存管理 token

### FR-2 进入投票（源 G-002）
- FR-2.1 房间链接形如 `/r/<room-id>`；访问不存在 / 已关闭的房间返回 404 / 410 + 友好文案
- FR-2.2 首次进入时为浏览器分配 **参与者 token**（HttpOnly cookie 或 localStorage 二选一，由 PLAN 决定）；同 token 视为同一参与者
- FR-2.3 不要求登录 / 邮箱 / 手机号 / 昵称（最简匿名）

### FR-3 投票（源 G-003）
- FR-3.1 投票页展示房间标题 + 候选项复选框；至少勾 1 项才允许提交
- FR-3.2 提交后服务端按「参与者 token + 房间 id」存储该参与者当前选择（覆盖式）
- FR-3.3 已投票的参与者可重新修改选择，直到房间被关闭

### FR-4 追加候选项（源 G-004）
- FR-4.1 当房间 `allow_add == true` 且未关闭时，投票页显示"+ 添加候选项"按钮
- FR-4.2 任意参与者可追加候选项；服务端对同房间内重复文本（去空白后 case-insensitive 比较）做去重，已存在则提示并不重复创建
- FR-4.3 追加的候选项立即对该房间所有打开页面的参与者可见（实时更新机制见 FR-5）

### FR-5 实时结果（源 G-005）
- FR-5.1 投票页顶部 / 旁边显示「当前总参与人数」与「每个候选项的当前票数」
- FR-5.2 票数变化在 p95 ≤ 2s 内对所有打开页面的参与者可见（实现可选轮询或 SSE，由 PLAN 决定）
- FR-5.3 票数展示形式：横向条形图或纯文本"N 票 (X%)"任选其一（由 STORY/PLAN 决定）

### FR-6 持久化（源 G-006）
- FR-6.1 房间、候选项、投票三类实体写入本地 SQLite 文件
- FR-6.2 服务重启后通过原链接仍可访问；票数、候选项、参与者 token 关系不丢失
- FR-6.3 SQLite 文件路径可通过环境变量配置；默认 `./data/voting.sqlite`

### FR-7 房间管理（来自 OQ-3 决议：保留管理 token）
- FR-7.1 凭管理 token 可关闭房间（标记 `closed_at`），关闭后不再接受新投票 / 新候选项；结果页仍可查看
- FR-7.2 凭管理 token 可删除单个候选项（已投该项的票一并撤销）
- FR-7.3 管理 token 不在 URL 中明文出现；通过请求头或表单字段提交

## Non-Functional Requirements

### NFR-1 性能
- 单房间在线参与者 ≤ 50 人
- 实时刷新 p95 < 2s（FR-5.2）
- 创建 / 投票 / 拉结果 API p95 < 300ms（本地 SQLite，典型机器）

### NFR-2 可访问性（WCAG 2.1 AA 关键项）
- 所有交互元素键盘可达，焦点可见
- 表单输入有显式 `<label>`，错误提示 `aria-live` 或同级文本
- 文字 / 背景对比度 ≥ 4.5:1（正文）/ 3:1（大字号）
- 不强制色彩唯一传达（票数 + 文字数值，而不只是颜色条）
- 非目标：完整屏幕阅读器优化（仅保证基础语义）

### NFR-3 安全 / 反作弊
- 管理 token 至少 32 位随机熵；服务端按房间存储 hash
- 参与者 token 仅作软性"同一浏览器"识别；明确接受清浏览器即可重投的弱模型
- 输入字段服务端做长度上限校验（标题 120 / 候选项 80 字符），避免存储膨胀
- 不引入第三方 captcha / 频率限制（本期 Non-Goals）

### NFR-4 可观测
- 服务端写结构化日志：创建房间、投票、追加候选项、关闭房间，含房间 id（不含管理 token）
- 不接外部 APM；本地教学场景，stdout 即可

### NFR-5 部署 / 兼容
- 单进程启动，无外部依赖（除运行时与 SQLite）
- 现代浏览器（Chrome / Firefox / Safari 最新两个大版本）
- 中文 UI 优先，文案集中可改

## Acceptance Criteria（汇总，便于 STORY 阶段直接抄）

- [ ] 任意用户能在 < 1 分钟内通过 Web 表单创建一个含 3 候选项的投票，并得到可分享链接
- [ ] 第二个浏览器（无痕窗口）打开链接能匿名投票、勾多选并提交成功
- [ ] 两个浏览器并发投票时，双方在 ≤ 2s 内看到对方的票数变化
- [ ] 开启「允许追加」时，参与者新增候选项立即对另一个窗口可见
- [ ] 关闭「允许追加」时，投票页看不到追加入口
- [ ] 服务重启后通过原链接仍能访问房间，票数无丢失
- [ ] 发起人凭管理 token 可关闭房间；关闭后投票按钮置灰且 API 返回明确错误
- [ ] 键盘 Tab 可遍历所有可交互元素；提交按钮按 Enter 生效
- [ ] 非法 / 已关闭房间访问返回 404 / 410 + 中文友好提示

## Open Questions（留给 STORY/PLAN 续问）

- **OQ-1**（源 REQ）实时同步用轮询还是 SSE / WebSocket？★ 默认轮询（最简单）。PLAN 阶段决定。
- **OQ-2**（源 REQ）截止时间字段本期不做（已决议进入 Non-Goals）。
- **OQ-4**（源 REQ）技术栈选型？★ 默认 FastAPI + Jinja + 原生 JS + SQLite（最少依赖，教学友好）；也可换 Next.js + better-sqlite3。PLAN 阶段决定。
- **OQ-5**（源 REQ）二维码方便手机扫码进入 — 本期标 nice-to-have，可视作独立 STORY 是否纳入由 STORY 阶段决定。
- **OQ-6**（新增）参与者 token 落 cookie 还是 localStorage？★ 默认 HttpOnly cookie（更标准）。PLAN 决定。
- **OQ-7**（新增）UI 文案是否需 i18n？★ 默认仅中文硬编码，i18n Non-Goal。

## Risks

- **R-1** SQLite 并发写入瓶颈：50 人量级 + WAL 模式应足够；监控写延迟即可。
- **R-2** "清浏览器即可重投"被滥用：本期接受，写明在 README；如反馈强烈再开新 REQ。
- **R-3** 实时机制选错导致延迟超标：先做轮询验证 2s 阈值，必要时再迁 SSE。
- **R-4** 管理 token 丢失即失去管理权：本期不支持找回（写在 FAQ）；后续可考虑邮箱备份选项。
