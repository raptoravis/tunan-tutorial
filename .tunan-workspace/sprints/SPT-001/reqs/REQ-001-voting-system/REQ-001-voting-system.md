# REQ-001 轻量投票系统

## 用户原话

> 我想做一个投票系统：可以投票去哪里旅游 / 中饭吃什么。

## 意图概括

为小团体（同事 / 朋友 / 家人）提供一个**轻量、低门槛、可分享**的投票工具，覆盖"今天中饭吃什么"、"周末去哪玩"等高频小决策场景。发起 → 分享链接 → 多人投票 → 看到结果，整个过程应当在分钟级完成，不需要账号。

## Goals

- **G-001**：发起人能在 ≤ 1 分钟内创建一个新投票（含标题 + 2..N 个选项 + 截止时间）
  - [ ] 创建表单允许至少 2 个、最多 20 个选项
  - [ ] 标题与每个选项内容非空、长度 ≤ 100 字符
  - [ ] 截止时间必须是未来时刻；过期投票自动进入"已结束"态
  - [ ] 创建成功后返回一个**可分享的短链/URL**

- **G-002**：参与者通过链接打开投票页，可在不登录的前提下完成一次投票
  - [ ] 默认单选；多选作为 Open Question 推到 PRD
  - [ ] 同一参与者**单次投票防重复**（来源：R1）：基于浏览器端标识（如 localStorage + 后端校验）保证一人一票，允许在截止前改票
  - [ ] 投票后立刻看到当前结果
  - [ ] 投票截止后只能查看结果不能投票（来源：R5）

- **G-003**：结果以**条形 + 百分比**形式可视化呈现（来源：R4）
  - [ ] 每个选项显示得票数与占比
  - [ ] 总得票数显眼展示
  - [ ] 截止时间倒计时（未结束）或"已结束 + 截止时间"标签（已结束）

- **G-004**：a11y 基础（来源：R3）
  - [ ] 投票表单全部控件可纯键盘操作（Tab / Enter / Space）
  - [ ] 焦点可见（无 `outline: none` 裸用）
  - [ ] 关键按钮（提交、复制链接）有合理的 aria-label
  - [ ] 颜色对比度满足 WCAG AA（仅对成品色板做一次核对，不深挖）

- **G-005**：投票数据跨端共享（决定本 REQ 选择"前端 + 简单后端"形态）
  - [ ] 后端持久化投票元数据与每票记录
  - [ ] 不同设备打开同一链接看到一致结果
  - [ ] 后端形态在 PRD 阶段决定（Node Express / Cloudflare Workers + KV / 等）

## Constraints

- 教学项目（`tunan-tutorial.git`），代码可读性 > 性能极致
- 不引入账号系统（v1）；防重复仅做"诚实用户"级别（同浏览器 + 后端轻校验），不抗专业刷票
- Windows 优先开发环境（与本仓库现有约束一致）
- 后端形态需可本地起、易部署；不强行上 K8s / 复杂中间件

## Non-Goals (v1 明确不做)

- 账号系统 / 实名 / OAuth 登录
- 反作弊 / 验证码 / IP 限制 / 风控
- 多语言 i18n
- 移动 App 原生端（仅 Web，移动浏览器适配即可）
- 投票数据导出 / 第三方集成（Slack / 微信）
- 修改 / 删除已发布的投票（仅截止前可改票，不可改题）
- 主题分类（旅游 / 午餐分门别类的运营功能）；当前所有投票一视同仁

## Scope Boundary

**In scope (v1)：**
- 创建投票（标题、2..N 选项、截止时间）
- 通过 URL 分享
- 投票（单选）+ 改票（截止前）
- 看结果（条形 + 百分比 + 总数）
- a11y 基础
- 后端持久化

**Out of scope (推到后续 REQ)：**
- 多选 / 评分 / 排序投票
- 参与者补加选项
- 评论 / 讨论区
- 数据分析仪表盘
- 任何形式的账号与权限

## Open Questions (推到 tunan-prd 续问)

- **OQ-1 投票形式扩展**：v1 仅单选，是否在 PRD 阶段就预留"多选 / 评分"的数据模型？  
  - ★ 默认：v1 数据模型只承载单选；多选作为 v2 REQ
  - B：数据模型直接预留多选字段，UI 暂只露单选
  - C：现在就纳入多选 UI（**会显著扩大 v1 STORY 数**）

- **OQ-2 选项来源**：是否允许参与者补加选项（如"还有人想去的地方？"）？  
  - ★ 默认：仅发起人定义选项（v1）；补加放 v2
  - B：参与者可建议、发起人审核
  - C：参与者直接加（开放协作）

- **OQ-3 短链形态**：URL 的 slug 用什么策略？  
  - ★ 默认：随机 8 字符（base62），不可猜测
  - B：自增 id（URL 短但可枚举）
  - C：发起人自定义 slug（可读性好，但要查重）

- **OQ-4 后端栈选择**：交给 tunan-prd 阶段拍板（Node + SQLite / Cloudflare Workers + KV / Hono + D1 / ...）

- **OQ-5 防重复的具体实现强度**：  
  - ★ 默认：localStorage 标识 + 后端按 (poll_id, voter_token) 唯一约束；清缓存可重投（接受）
  - B：加 IP 维度
  - C：纯前端 localStorage（最弱）

## Research Findings

| # | 发现 | 处理 |
|---|---|---|
| R1 | 重复投票是同类工具最常见崩点 | 进 G-002 acceptance |
| R2 | 移动端 + 短链分享是主流入口 | URL 短链进 G-001，移动浏览器适配进 a11y 间接覆盖 |
| R3 | a11y 易被忽视、长期债 | 进 G-004 |
| R4 | 条形 + 百分比比纯数字更易读 | 进 G-003 |
| R5 | 截止时间缺失导致 UX 不闭环 | 进 G-001 / G-002 |
| R6 | tutorial 项目易因账号系统过早把范围做爆 | 已写入 Non-Goals |
